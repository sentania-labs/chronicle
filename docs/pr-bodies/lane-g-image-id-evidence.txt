Probe, issue 47 (Store.get_image builds a path from an unchecked image id).
Run 2026-09-19, about 23:31 America/Chicago, against a real uvicorn on 127.0.0.1:8391 (branch
feat/store-burndown at 31f38b6, before any change), fresh data directory under /tmp/laneg.
Consumer token redacted; every request otherwise verbatim (curl --path-as-is, so the client does
not normalise the path). Response headers date/server are dropped; the rest is unedited.
Convention followed: docs/pr-bodies/lane-g-queue-timeout-evidence.txt.
The probe script is reproduced at the end of this file; both runs used it unchanged.

How the path is built: images_dir / id[:2] / f"{id}.json". A file named X.json planted OUTSIDE
data/images is reachable when id[:2] is ".." and the id itself is one path segment (no slash),
because "images/../" + "..." + ".json" is data/...json. Ids that carry a slash never reach the
store: the router's {image_id} parameter does not match "/" (literal or after percent-decoding).

################################################################
# Callers that reach get_image with an id the caller did not mint
################################################################
- GET /v1/images/{image_id}: passed the raw URL segment. Guarded by the fix (this probe).
- PUT /v1/drafts/{draft_id}/images/{image_id} (attach): raw URL segment through
  attach_image -> get_image. Before: accepted "..". After: 404 (this probe).
- DELETE /v1/drafts/{draft_id}/images/{image_id} (detach): never calls get_image; it only
  compares the id against the draft's own attached list, so it builds no path. Unchanged.
- GET /content/drafts/{draft_id}/images/{image_id}/file (UI file route): checks the id is
  attached to the draft first, then get_image and image_blob (which calls get_image first).
  It was safe only because attach had let ".." in; with the attach closed and get_image
  guarded it is closed on both sides. (UI file, read only, not edited.)
- POST/PUT /v1/submissions image_ids: validated by _image_exists (_IMAGE_ID fullmatch) on create
  and revise (probe above: 422 image_not_found for "../../planted-image"). submission_images()
  guards with _image_exists too. The one unguarded reader was the seed loop in
  _seed_draft_from_submission, which called get_image directly on stored ids; it catches
  ApiError, and get_image now raises ApiError for a malformed id, so a legacy bad id is a
  warning there, never a path.

Regression tests: tests/test_api_images.py (test_get_image_refuses_an_id_that_is_not_a_sha256,
test_get_image_does_not_read_a_file_outside_the_images_directory,
test_image_routes_refuse_an_encoded_dotdot_id).
Note for anyone rerunning this with an HTTP test client: httpx normalises a literal ".." away
before sending, which is why the literal form is proved here with curl --path-as-is.

# Probe for issue 47: can GET /v1/images/{id} read a file outside data/images?
# usage: probe47.sh <label>
set -u

# Plant two files there: a valid Image-shaped record, and an arbitrary secret.
cat > "$ROOT/planted-image.json" <<J

J
echo '{"db_password":"hunter2-SECRET-NOT-AN-IMAGE-RECORD"}' > "$ROOT/secret.json"
# and one directly in data/, reachable through the bare ".." id: data/...json

{"image_id":"DOTDOTDOT","sha256":"0","filename":"dots.png","bytes":1,"mime":"image/png"}
J
echo "== planted files (outside data/images):"

uv run uvicorn chronicle.api.main:app --host 127.0.0.1 --port 8391 --log-level warning >"$ROOT/uvicorn.log" 2>&1 &
PID=$!
trap 'kill $PID 2>/dev/null; wait $PID 2>/dev/null' EXIT
for i in $(seq 1 60); do curl -sf http://127.0.0.1:8391/healthz >/dev/null && break; sleep 0.5; done

probe() {
  local label="$1" path="$2"

probe "double-encoded %252f" "/v1/images/..%252f..%252fplanted-image"
probe "encoded dots %2e%2e%2f" "/v1/images/%2e%2e%2f%2e%2e%2fplanted-image"

echo
echo "== other callers that reach get_image with a caller-chosen id"
