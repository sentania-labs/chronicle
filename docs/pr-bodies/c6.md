# C6: image directory rule, backup and restore, release CI, reference manifests

## TLDR

Chronicle now has a single url-derived image directory rule for imported
and new drafts (ADR 015), full backup and restore (spec section 13, ADR
016) with an admin page for it, a release pipeline that ships signed,
SBOM-attached images only on a `v*` tag (ADR unnecessary, coppermind's
shape), `compose-smoke` gating pull requests, finished k8s reference
manifests, a CSP header, and pagination. `make check` is green (386 tests).
All three required live checks pass: the three-post image path diff is
byte-identical against the real blog clone, a full backup/restore round
trip across two fresh stacks reproduced identical counts and a rebuilt
preview served, and `make compose-smoke` passed locally. An adversarial
review of the diff found six real issues, all fixed on this branch with
regression tests: a CSP-broken UI control, an unusable restore-upload size
ceiling, a bypassable image-directory collision check, a backup/restore
race with the api's own background threads, a checksum race in backup
creation, and a release job that could fail after images were already
pushed. Docs, ADRs, and AGENTS.md are updated.

## What changed

- **Image directory rule** (ADR 015): `static/images/<post slug>/` is
  always the last non-empty path segment of the post's `url`, or the
  pinned slug when there is none, for both imported and new drafts. Never
  the dated digest filename. `Draft.image_dir` is set once, at import
  (`_fill_from_post`) or at first pin (`_pin_slug`), and read as-is by
  `convert.convert`, the publisher's unpublish delete set, and the
  builder's copy. Pinning refuses (409 `image_dir_collision`) when another
  draft already pins the directory or it already exists on main for a
  different post.
- **Backup and restore** (spec section 13, ADR 016): `chronicle backup
  create` tars `repo/` (with `.git`), `images/`, and the encrypted portion
  of `state/`, with a `manifest.json` of per-member sha256 and record
  counts; never `instance.key`, `preview/`, `site/`, `builder-work/`,
  `claim-code`, or `ui_token.txt`. `chronicle backup restore` validates the
  manifest and every checksum before touching the data directory, swaps
  `repo/` and `images/` and the state files atomically, keeps the displaced
  tree until reindex succeeds, and initialises git history on a bundle with
  no `.git`. Admin page at `/admin/backup`: create/download, last-backup
  time, upload with a manifest-count confirmation step that requires typing
  `restore`.
- **Release CI** (spec section 14, coppermind's shape):
  `.github/workflows/ci.yml` adds `release-tag` validation (annotated,
  `v[0-9]+.[0-9]+.[0-9]+`, on main), and on a `v*` tag push only: build all
  three images once each, SBOM attached, pushed to `ghcr.io/sentania-labs/*`
  under the immutable version tag (refuses if it already exists), signed
  with cosign keyless, verified in the same job, then a GitHub release with
  notes from merged PR titles since the previous tag. `compose-smoke` gates
  every pull request from the `sentania-labs` fork. Every action is pinned
  by SHA; only `publish` carries `packages: write` / `id-token: write`.
- **Reference k8s manifests**: `examples/k8s/` finished (Deployment with
  the three containers, `fsGroup`/`runAsUser 1000`,
  `readOnlyRootFilesystem`, readiness/liveness probes, PVCs, instance-key
  Secret, internal Ingress, resource requests), a new `chronicle-builder
  --healthcheck` subcommand replacing the inline Python liveness probe
  (file-age check against the builder's heartbeat), and a README on
  adapting it for a real deployment.
- **Small folded-in items**: a Content-Security-Policy header
  (`default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self'
  data:`) on every response; pagination (page size 50, next/previous links,
  total count) on the drafts board, submissions list, and import list.
- **Docs**: README (backup, release, image rule), CONTRIBUTING.md (release
  procedure, `cosign verify`, packages-visibility note), `docs/backup.md`
  (bundle format precise enough to hand-build an import bundle), ADR 015,
  ADR 016, `examples/k8s/README.md`, AGENTS.md sharp edges.

## Adversarial review findings and disposition

One review subagent, given only `git diff main...HEAD`, scoped to this
round's changes. Six findings, all confirmed real by manual inspection and
fixed on the branch with regression tests (`make check` green afterward,
386 tests):

1. **CSP broke the drafts-board status filter.** The only remaining inline
   event handler (`onchange="this.form.submit()"`) did nothing once
   `default-src 'self'` shipped, with no `script-src` exception and no
   fallback submit button. Fixed: moved to `ui.js` (now loaded on every
   page, not only the editor), plus a plain submit button for no-JS.
   Commit `b1705dc`.
2. **The restore-upload size ceiling made the feature unusable.** The
   blanket 8 MiB `BodySizeLimitMiddleware` applied to
   `/admin/backup/upload` too; a real bundle (git history, every image)
   routinely exceeds that. Fixed: a per-path override, still bounded (512
   MiB, not exempted) since the route reads the whole upload into memory.
   Commit `58ce9a4`.
3. **The image-directory collision check didn't cover imports.**
   `_pin_slug`'s collision check only runs when `act_on_draft` finds
   `draft.slug is None`, which is never true for an import
   (`_fill_from_post` sets both directly). A second import of the same
   post, or a different post landing on the same url-derived directory,
   silently shared `static/images/<dir>/` with a draft that already pinned
   it. Fixed: `_fill_from_post` now checks `pinned_image_dirs` the same way
   `_pin_slug` does (skipping only the "already exists on main" half, since
   a legitimate import's directory is exactly what's already there).
   Commit `e47f1a8`.
4. **The live restore raced the api's own background threads.**
   `restore_backup`'s own docstring says the api process must be stopped
   first (its swap is a bare `shutil.move`, not taken under any lock), but
   the admin route called it live and only stopped the publisher, watcher,
   reconcile threads, and closed the store *after* the swap via
   `reload_after_restore`. A write racing the swap landed in the
   pre-restore tree, which the same call then deletes. Fixed: split into
   `quiesce_for_restore` (called before `restore_backup`) and
   `resume_after_restore` (called after, in a `finally`, on both success
   and `BackupError`). Commit `58ce9a4`.
5. **Backup create hashed and tarred each file from two separate reads.**
   The api keeps writing while a backup runs; a file rewritten between the
   hash pass and `tar.add`'s own read produced a bundle whose manifest
   checksum didn't match its own tar member, and restore would refuse it as
   tampered with no fault on either side. Fixed: a `_HashingReader` wraps
   the single file handle `tar.addfile` streams from, so the hash and the
   tarred bytes are the same read; a file that vanishes mid-backup (a
   builder claiming a queue entry, a git repack) is dropped from the bundle
   instead of crashing the whole backup. Commit `6f86882`.
6. **The release job could fail after images were already pushed.**
   `release-notes.sh`'s `grep -E '\(#[0-9]+\)$' | sort -u` exits 1 under
   `set -o pipefail` when no commit in range matches the squash-merge
   subject shape, failing the `release` job (which runs after `publish`
   has already pushed and signed the immutable tags) with no GitHub release
   to show for it. Fixed: an empty match now prints a plain note instead of
   crashing. Verified by hand against a throwaway git repo built to
   reproduce the empty-match case (`exit=0`, prints "no merged pull
   requests found in this range"). Commit `819071d`.

No findings were dismissed as invalid; all six were real and fixed.

## Deviations from the spec

- The image directory rule (task's own instruction) amends
  `docs/spec/00-spec.md` section 17 with a single dated line (2026-09-17,
  Scott) rather than rewriting the section; ADR 015 carries the reasoning.
- `chronicle backup restore`'s CLI path documents itself as requiring a
  stopped api process (its swap is an unlocked `shutil.move`); the admin
  page's live restore is the one path that self-heals in-process instead
  (`quiesce_for_restore` / `resume_after_restore`, added this round after
  the adversarial review). The builder container still needs a manual
  restart after any restore, live or CLI, since it holds its own
  independent SQLite connection in a separate process; this is documented
  in `docs/backup.md` and the admin confirmation page, not automated.
- `chronicle backup create` is not taken under the store's lock (finding 5
  above narrows, but does not eliminate, the race with concurrent writes
  from the publisher/watcher/builder, since those are separate processes
  the in-process `threading.Lock` cannot reach). This matches the
  single-api-replica assumption ADR 013 already makes; a cross-process
  backup lock would be new scope, not a C6 fix.

## Not done, noticed

- Reconciliation's `slug_drift` and `content_drift` flags still offer only
  `ignore` as a resolution (unchanged from C4/C5 scope; not part of this
  round).
- A second api replica still has no lease discipline for the publisher or
  the restore quiesce/resume sequence added this round (both assume a
  single writer against the data directory, ADR 013); this remains a
  deliberate scope cut, not an oversight.
- `release-notes.sh`'s `previous_tag` selection
  (`git tag --list 'v*' --sort=-v:refname | grep -v "^${VERSION}\$" | head
  -n1`) picks the highest remaining tag, which is only the correct
  predecessor when tags are cut in increasing version order. A hotfix
  release for an older minor version after a newer one has already shipped
  would compute the wrong `previous_tag` and produce a misleading changelog
  range. Not fixed this round: Chronicle's own release history has no such
  case yet, and a correct fix needs semver-aware ordering, not a one-line
  change.
